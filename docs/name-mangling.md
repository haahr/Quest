# Quest C Transpiler Name Mangling Specification

This document specifies the complete name mangling and symbol generation rules implemented by the Quest bootstrap C
transpiler ([`c_types.py`](file:///Users/haahr/Dropbox/Paul/src/quest/bootstrap/python/quest/codegen/c_types.py),
[`c_declarations.py`](file:///Users/haahr/Dropbox/Paul/src/quest/bootstrap/python/quest/codegen/c_declarations.py),
[`c_emitter.py`](file:///Users/haahr/Dropbox/Paul/src/quest/bootstrap/python/quest/codegen/c_emitter.py), and
[`c_analysis.py`](file:///Users/haahr/Dropbox/Paul/src/quest/bootstrap/python/quest/codegen/c_analysis.py)).

It serves as the definitive reference for understanding any symbol, struct, typedef, parameter, or temporary variable
generated during Quest C code generation (`codegen_c`).

---

## 1. Design Principles & Namespacing

The Quest compiler targets ISO C99 (`clang` / `gcc`). To ensure safe, collision-free code generation across translation
units, name mangling adheres to the following principles:

1. **C Keyword & Libc Protection:** All Quest value and function identifiers are prefixed with `qv_` to prevent
   collisions with C keywords (`int`, `return`, `default`, `static`, `register`, `case`, etc.) and standard library
   symbols (`open`, `read`, `write`, `exit`, etc.).
2. **C Struct Keyword Protection:** All Quest record field names inside C structs are prefixed with `qf_`
   (e.g. `qf_default`, `qf_return`) to allow arbitrary Quest field identifiers without colliding with C reserved words.
3. **Hierarchical Module Separation:** Module paths are flattened using double underscores (`__`), preventing collisions
   between different packages having identically named submodules (e.g. `util/path` $\rightarrow$ `util__path`).
4. **Deterministic Operator Mapping:** Symbolic operators are mapped to ASCII identifier segments via an unambiguous
   translation table prefixed with `qv_sym_`.
5. **Clear Linkage Boundaries:** Symbols are cleanly partitioned into `extern` (cross-module ABI), `static`
   (translation-unit internal), and local/block scopes.
6. **Header Shadowing Prevention:** Generated C interface headers are prefixed with `q_` (e.g. `q_string.h`, `q_path.h`)
   to prevent shadowing C standard library headers like `<string.h>`.

## 2. Linkage and Visibility Classification

Every C identifier generated by the compiler belongs to one of three linkage scopes:

| Linkage | Scope | C Storage Class | Examples | Description |
| :--- | :--- | :--- | :--- | :--- |
| **External** | Cross-unit | `extern` / default | `qv_util__path`, `qv_mod_calc_init` | Public module ABI & init |
| **Internal** | Translation unit | `static` | `qv_fn_1`, `quest_type_Int` | Lambdas, descriptors, dicts |
| **Local** | Function body | Automatic / stack | `qv_x`, `_res_1`, `_tuple_2` | Let-bindings, temporaries |

## 3. Value and Identifier Mangling

### 3.1. Alphanumeric Identifiers (`mangle_ident`)
Standard Quest identifiers consisting of alphanumeric characters and underscores are prefixed with `qv_`.
Any internal dot characters (such as qualified names) are converted to single underscores:

$$\text{mangle\_ident}(name) = \text{"qv\_"} + name.\text{replace}(".", "\_")$$

- `let x = 10` $\rightarrow$ `qv_x`
- `let count = 0` $\rightarrow$ `qv_count`
- `let default = true` $\rightarrow$ `qv_default` (safe from C keyword collision)
- `let point.x = 5` $\rightarrow$ `qv_point_x`

### 3.2. Symbolic Operators (`mangle_symbolic_ident`)
When symbolic operators appear as first-class functions or bindings, they are mangled using the prefix `qv_sym_`.
Each symbol character is looked up in `SYMBOL_MANGLE_MAP`:

| Character | Mangled Name | Character | Mangled Name | Character | Mangled Name |
| :---: | :--- | :---: | :--- | :---: | :--- |
| `+` | `plus` | `!` | `bang` | `^` | `caret` |
| `-` | `minus` | `?` | `question` | `&` | `amp` |
| `*` | `star` | `:` | `colon` | `\|` | `pipe` |
| `/` | `slash` | `@` | `at` | `~` | `tilde` |
| `=` | `equals` | `#` | `hash` | `\\` | `backslash` |
| `<` | `lt` | `$` | `dollar` | `'` | `prime` |
| `>` | `gt` | `%` | `percent` | `.` | Boundary / dot |

Runs of alphanumeric characters between symbols are preserved. Consecutive symbol names are joined with underscores:

- `+` $\rightarrow$ `qv_sym_plus`
- `++` $\rightarrow$ `qv_sym_plus_plus`
- `-` $\rightarrow$ `qv_sym_minus`
- `*` $\rightarrow$ `qv_sym_star`
- `:=` $\rightarrow$ `qv_sym_colon_equals`
- `<>` $\rightarrow$ `qv_sym_lt_gt`
- `->` $\rightarrow$ `qv_sym_minus_gt`
- `\=` $\rightarrow$ `qv_sym_backslash_equals`
- `<+>` $\rightarrow$ `qv_sym_lt_plus_gt`

## 4. Module & Library Names

Modules may be top-level or hierarchically nested within subdirectories.

### 4.1. Hierarchical Module Path Flattening (`mangle_module_name`)
Hierarchical module paths are canonicalized, converted to lowercase, with `/` mapped to `__` and `.` mapped to `_`:

$$\text{mangle\_module\_name}(module) = module.\text{lower}().\text{replace}("/", "\_\_").\text{replace}(".", "\_")$$

- `calc` $\rightarrow$ `calc`
- `util/path` $\rightarrow$ `util__path`
- `collections/hashmap` $\rightarrow$ `collections__hashmap`
- `net/http/client` $\rightarrow$ `net__http__client`

### 4.2. Module Record Instance
Every compiled Quest module produces a single global `QRecordVal` holding its exported interface record:
- **Definition (in module):** `QRecordVal qv_<clean_mod>;`
  - E.g. `QRecordVal qv_calc;`, `QRecordVal qv_util__path;`
- **Import declaration (in consumers):** `extern QRecordVal qv_<clean_mod>;`

### 4.3. Module Initialization Function & Guard
Each module defines an idempotent initialization function that initializes imported dependencies before evaluating
module-level bindings:
- **Init function:** `void qv_mod_<clean_mod>_init(void);`
  - E.g. `void qv_mod_calc_init(void);`, `void qv_mod_util__path_init(void);`
- **Consumer declaration:** `extern void qv_mod_<clean_mod>_init(void);`
- **Internal initialization flag (static):**
  - `static bool qv_mod_<clean_mod>_initialized = false;`

### 4.4. Module Top-Level Values and Functions (`mangle_module_ident`)
Identifiers defined at the top level of a module are prefixed with `qv_<clean_mod>_`:
- **Alphanumeric:** `qv_<clean_mod>_<name>`
  - E.g. `qv_calc_add`, `qv_util__path_join`
- **Symbolic operator:** `qv_<clean_mod>_sym_<parts>`
  - E.g. `qv_int_sym_plus`

### 4.5. Function Trampolines
When a module exports a function in its interface record, the compiler emits a static trampoline function to adapt the
top-level C function into a standard Quest closure (`QClosure`):
- **Pattern:** `static QClosure qv_<clean_mod>_<name>_trampoline(...)`
  - E.g. `static QClosure qv_calc_add_trampoline(...)`

### 4.6. Module Local Payload Pointer
During module initialization, the record payload is populated via a local typed pointer:
- **Pattern:** `_<clean_mod>_payload`
  - E.g. `struct QT_record1 *_util__path_payload = quest_alloc_record(...);`

### 4.7. Interface C Header Files
To avoid collision with C runtime and system headers (e.g. `<string.h>`):
- **Pattern:** `q_<interface_stem>.h`
  - E.g. `q_string.h`, `q_path.h`, `q_calc.h`

## 5. Functions, Closures, & Specializations

### 5.1. Main Program Functions
Top-level functions in a standalone main program are emitted with `static` linkage:
- **Pattern:** `static <return_type> qv_<name>(<params>)`
  - E.g. `static QInt qv_factorial(QInt qv_n)`

### 5.2. Lifted Lambdas and Closures
Anonymous functions and closures are lifted to static functions identified by unique sequence IDs:
- **Lifted function name:** `static <return_type> qv_<id>(void *_raw_env, <params>)`
  - E.g. `static QInt qv_fn_1(void *_raw_env, QInt qv_x)`
- **Environment structure:** `struct QEnv_<id>`
  - E.g. `struct QEnv_fn_1 { QInt qv_multiplier; };`
- **Environment unpacked pointer:**
  - `struct QEnv_<id> *_env = (struct QEnv_<id> *)_raw_env;`
- **Stateless closure singleton:** For lambdas with no free variables, a single static closure is emitted:
  - `static const QClosure qv_<id>_closure = { (void *)qv_<id>, NULL };`

### 5.3. Monomorphized / Specialized Functions
Calls to polymorphic functions with concrete types (records, variants, tuples) are specialized at call-sites:
- **Pattern:** `qv_<name>_spec_<type_tags>` or `qv_<clean_mod>_<name>_spec_<type_tags>`
- **Type tag mapping:** Built via `type_to_c_tag(t)`:
  - `Int` $\rightarrow$ `Int`, `String` $\rightarrow$ `String`, `Bool` $\rightarrow$ `Bool`, `Real` $\rightarrow$ `Real`
- **Examples:**
  - `qv_identity_spec_Int`
  - `qv_map_spec_String_Int`
  - `qv_collections__vector_push_spec_Int`

### 5.4. Type-Application and Coercion Adapters
When functions are passed through subtype coercions or type applications:
- **Adapter function:** `qv_adapt_<counter>` or `qv_typeapp_<counter>`
- **Adapter environment:** `QTypeAppEnv_qv_typeapp_<counter>`

## 6. Types, Aggregates, & Fields

### 6.1. Record Structs and Fields
- **Record struct tag:** `struct QT_<name>` (managed by `RecordNamingContext`):
  - Aliased records: `struct QT_<TypeName>` (e.g. `struct QT_Point`)
  - Anonymous / structural records: `struct QT_record<N>` or `struct QT_<module>_record<N>`
  - Structural fallback: `struct QRecord_<fld1>_<t1>_<fld2>_<t2>`
- **Record Header:** All record structs start with `QRecordHeader header;` (storing type descriptor pointer).
- **Record Field Mangling:** Every record field name is prefixed with `qf_`:
  - `qf_<field_name>`
  - E.g. `qf_x`, `qf_name`, `qf_default`, `qf_return`
  - Field access in C: `rec->qf_x` or `payload->qf_name`

### 6.2. Tuple Structs and Fields
- **Tuple struct tag:** `struct QTuple_<type1>_<type2>...`
  - E.g. `struct QTuple_Int_String`, `struct QTuple_Int_Int_Bool`
- **Tuple Fields:** Positional 0-indexed fields:
  - `_0`, `_1`, `_2`, ...
  - Access in C: `tup._0`, `tup._1`

### 6.3. Variant Structs and Union Branches
- **Variant struct tag:** `struct QVariant_<tag1>_<type1>_<tag2>_<type2>...`
  - E.g. `struct QVariant_leaf_Int_node_QVal`
- **Variant Members:**
  - `int64_t tag;`
  - `union { ... } u;`
- **Payload struct tags:** `struct <variant_tag>_<case_name>_payload`

### 6.4. Option Structs and Union Branches
- **Option struct tag:** `struct QOption_<tag1>_<type1>_<tag2>_<type2>...`
  - E.g. `struct QOption_none_some_Int`
- **Option Members:**
  - `int64_t tag;`
  - `union { ... } u;` with nested branch structs containing payload `val` or `qf_<field>`.

### 6.5. Subtyping Evidence Dictionaries
Quest supports Cardelli record width and depth subtyping via static offset dictionaries passed in fat pointers:
- **Dictionary struct type:** `struct OffsetDict_<record_name>` (typedef `OffsetDict_<record_name>`)
  - Members: `size_t offset_<field_name>;`
  - E.g. `struct OffsetDict_record1 { size_t offset_x; size_t offset_y; };`
- **Static dictionary instance:**
  - `static const OffsetDict_<target> offsetdict_<target>_<source> = { offsetof(...), ... };`
  - E.g. `static const OffsetDict_record1 offsetdict_record1_record2 = { offsetof(struct QT_record2, qf_x), ... };`

### 6.6. Variant Tag Remapping Tables
When a variant is coerced to a supertype variant:
- **Static remapping array:**
  - `static const int64_t tagmap_<tgt_tag>_<src_tag>[<case_count>] = { ... };`

### 6.7. Tuple Layout Assertions
Tuple structural subtyping is verified at compile time with C11/C99 static assertions:
- **Static assertion identifier:** `tuple_coercion_<tgt>_<src>_<index>`

### 6.8. Runtime Type Descriptors
Dynamic typing and existential ADTs utilize runtime descriptors:
- **Global descriptor instance:** `static const QTypeDescriptor quest_type_<tag>`
- **Record descriptor:** `static const QRecordTypeDescriptor qrec_desc_<tag>`
- **Tuple descriptor:** `qtup_desc_<tag>`
- **Variant / Option descriptor:** `qvar_desc_<tag>`

## 7. Parameters and Generated Temporaries

### 7.1. Function Parameters
- **Normal parameters:** `qv_<param_name>` (e.g. `qv_x`, `qv_len`)
- **Module function export parameters:** `qv_p_<param_name>` (e.g. `qv_p_a`, `qv_p_b`)
- **Type descriptor parameters (polymorphic descriptors):** `descriptor_<quantifier_name>` (e.g. `descriptor_T`)
- **Adapter positional parameters:** `qv_arg_<index>` (e.g. `qv_arg_0`, `qv_arg_1`)

### 7.2. Temporary Expression Variables (`fresh_tmp`)
During expression lowering, `CEmitter.fresh_tmp(prefix)` generates distinct temporary variables with unique integer
suffixes (`<prefix>_<counter>`):

| Prefix | Usage / Context | Typical Emitted Code |
| :--- | :--- | :--- |
| `_res_<n>` | General expression result | `QInt _res_1 = qv_a + qv_b;` |
| `_if_res_<n>` | If-then-else expression result | `QBool _if_res_2;` |
| `_call_res_<n>` | Direct function call result | `QString *_call_res_3 = qv_concat(...);` |
| `_call_ret_<n>` | Indirect closure call return | `QVal _call_ret_4 = ((QVal (*)...)(clos.fn))(...);` |
| `_tuple_<n>` | Tuple allocation & construction | `struct QTuple_Int_Int _tuple_5 = { ... };` |
| `_tsrc_<n>`, `_tup_up_<n>` | Tuple unpacking and coercion | `_tup_up_6._0 = _tsrc_7._0;` |
| `_rec_<n>`, `_rec_payload_<n>` | Record allocation and packing | `struct QT_record1 *_rec_payload_8 = ...;` |
| `_clos_<n>` | Heap-allocated closure struct | `QClosure *_clos_9 = quest_alloc_closure(...);` |
| `_env_<n>` | Heap-allocated closure environment | `struct QEnv_fn_1 *_env_10 = quest_alloc(...);` |
| `_var_<n>` | Variant value construction | `QVariantVal _var_11 = { .tag = 0, ... };` |
| `_opt_<n>`, `_unpacked_opt_<n>` | Option construction / unpacking | `QOptionVal _opt_12 = { ... };` |
| `_case_tgt_<n>`, `_vtgt_<n>` | Target of `case` branch matching | `QVariantVal _case_tgt_13 = ...;` |
| `_var_cell_<n>` | Heap cell for mutable `var` binding | `QVarVal _var_cell_14 = quest_alloc_var(...);` |
| `_loc_ptr_<n>` | Pointer to mutable variable | `QInt *_loc_ptr_15 = &qv_x;` |
| `_shadow_cell_<n>` | Mutable variable capture cell | `_shadow_cell_16->val = ...;` |
| `_qh_<n>`, `_caught_<n>` | Exception handler context and caught value | `QExceptionHandler _qh_17;` |
| `_insp_tgt_<n>`, `_insp_val_<n>` | Dynamic type inspect target and payload | `QDynamicVal _insp_tgt_18 = ...;` |
| `_stop_<n>` | Loop upper bound evaluation | `QInt _stop_19 = qv_n;` |
